# Forgent Engineering & Repository Guidelines

This document governs all agent and human contributions to the Forgent codebase. Every agent working in this repository must strictly adhere to these standards.

---

## 1. File Structure & Modularity Directives

1. **Strict Line Count Limits:**
   - **No file may exceed 1,000 lines of code.**
   - Optimal module target: 200–600 lines.
   - If a file approaches 800 lines, immediately extract helper logic, types, or child components into dedicated sibling modules.
2. **Self-Descriptive Naming:**
   - Every file name must plainly and simply explain its contents (e.g., `agent-card.tsx`, `execution-stepper.tsx`, `verify-evidence.ts`).
   - Use kebab-case for filenames (`kebab-case.ts`, `kebab-case.tsx`).
   - Avoid generic, vague names like `utils.ts`, `helpers.ts`, `manager.ts`, or `misc.ts`.

---

## 2. Commit & Version Control Standards

1. **Clean, Human-Readable Commits:**
   - Follow Conventional Commits format: `<type>(<scope>): <subject>` (e.g., `feat(marketplace): add category filter tabs`, `fix(env): add offline fallback for database url`).
   - Keep messages concise, imperative, and straight to the point.
   - **Zero AI-slop or agent trailers:** Never add "Co-authored-by: <agent>", "Generated by AI", or promotional filler to commit messages or pull requests.
2. **Atomic Commits:**
   - Each commit must represent a single logical change that compiles and passes typechecks.

---

## 3. Architecture & Code Quality Principles

1. **The Ponytail Code Economy (YAGNI):**
   - Write the simplest, shortest, most robust working code.
   - Reuse existing utilities and standard library APIs before installing third-party npm packages.
   - Avoid premature abstraction, deep inheritance, or speculative boilerplate.
2. **Type Safety & Schema Integrity:**
   - Strict TypeScript: Zero `any` types. All database entities, API payloads, and form inputs must be typed with Zod schemas.
   - Maintain paise precision (`Int`) for all monetary fields; never use floating-point numbers for currency.
3. **Defensive Offline Resilience:**
   - The application must build and pass offline tests cleanly. Fallback to mock environments gracefully when external services (Neon, QStash) are unreachable.
4. **Anti-Slop UI Craft (Hallmark Standard):**
   - Interfaces must look custom-crafted, not AI-templated.
   - Tokenize all colors and typography at `:root` or Tailwind configuration (Porcelain White `#F5F9FD`, Deep Royal Cobalt `#0B4FBA`, Azure `#5EA2FF`, `Italiana` serif headings, `Jeju Gothic` UI).
   - Avoid purple-to-blue gradients, nested cards inside cards, and generic SaaS templates.
   - Design for accessibility: visible focus rings, responsive viewports, and clean contrast.
5. **Strict Zero-Emoji Policy:**
   - **Never use emojis in the actual website UI.** No emojis in buttons, badges, headings, cards, navigation, or status indicators.
   - Use clean, professional monochrome SVG icons (e.g., Lucide React icons) styled to match the cobalt/graphite theme.
6. **Zero AI-Slop Writing & Copywriting Standards (Humanizer Rules):**
   - Ban all robotic AI marketing clichés: "Unleash the power of...", "In today's fast-paced digital landscape...", "Seamlessly revolutionize...", "Supercharge your productivity...", "Game-changing", "Next-gen", "Pave the way".
   - Write like a senior engineer writing technical documentation for Stripe or Linear: direct, active voice, plain language, and mathematically precise facts.
   - State what the product does, what it costs, and how it is verified. Nothing more, nothing less.
