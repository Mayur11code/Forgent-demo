## 3. How to update this tracker

1. Every task has exactly one stable ID and one directly responsible workstream. Do not renumber existing tasks.
2. Every task has exactly one owner workstream, but another workstream may collaborate. Record collaborators in the task description or a decision entry.
3. Dependencies must use task IDs. If a dependency is removed, record why in 16_DECISIONS_AND_CHANGELOG.md.
4. Change status only in this canonical file. Then update `TASK_TRACKER.csv` by regeneration or a single consistent edit; never maintain two divergent trackers.
5. `BLOCKED` requires a written blocker in the Blocker column: what is missing, who owns it and what unblocks it. An empty blocker is invalid.
6. A task may be marked `DONE` only when its acceptance criteria pass and its verification method has been run. Code written is not done.
7. A phase requires the phase gate to pass, the integrated prototype to be usable, and a checkpoint commit/tag. Update the Phase Board.
8. Move dropped scope to `DROPPED` with a reason; do not delete the row. Record deferred items in the Deferred register.
9. Update the Summary counts whenever a status changes.
10. Record material interface, scope or economics changes in the decision log before implementation continues.
11. Preserve IDs when tasks move or split. Mark the old ID `DROPPED` with "superseded by …" and create the replacement with a new ID.
12. At each checkpoint, run the phase smoke test and attach the result to the checkpoint note. Tag format: `p0-foundation`, `p1-shell`, … `v1.0-demo`.

### Status values

| Status | Meaning |
|---|---|
| `NOT_STARTED` | Default state. Work has not begun. |
| `IN_PROGRESS` | Developer has checked out the branch and started coding. |
| `BLOCKED` | Cannot proceed; blocker text is mandatory. |
| `REVIEW` | Implementation complete; acceptance verification or cross-team review pending. |
| `DONE` | Acceptance criteria and verification method passed. |
| `DROPPED` | Removed or deferred; reason recorded; row preserved. |

### Priority values

| Priority | Meaning |
|---|---|
| `P0` | Essential for the complete demo. Protect on the critical path. |
| `P1` | Important for a premium or complete experience. |
| `P2` | Desirable only if P0/P1 is green. |
| `P3` | Post-hackathon or explicitly deferred. |

### Kind values

| Kind | Meaning |
|---|---|
| `CRITICAL` | On the primary demo path or an unskippable gate deliverable. |
| `PARALLEL` | Core work that runs in parallel with another stream; cannot be cut. |
| `INTEGRATION` | Joint checkpoint, contract sign-off, or cross-workstream verification. |
| `OPTIONAL` | Enhances the experience but can be dropped if a phase runs long. |
| `DEFERRED` | Out of 24-hour scope; recorded for post-hackathon roadmaps. |
